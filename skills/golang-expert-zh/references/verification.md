# Go 验证与审查

## 工具与模块范围

先从 `go.work`、目标 `go.mod`、构建标签、Makefile 和 CI 找入口。以下为无仓库封装时的命令形态，在目标 Module 目录执行；不能假设一个 `./...` 覆盖仓库的全部 Module。

| 目标 | 命令或方式 | 使用条件 |
|---|---|---|
| 格式 | `gofmt -l path/to/changed.go` | 列出差异，按任务范围格式化 |
| 静态检查 | `go vet ./...`，已有 staticcheck/golangci-lint | 使用已锁定工具配置，不新增全仓告警债务 |
| 行为与编译 | `go test ./...` 或目标包和用例 | 使用实际 tags、CGO 和测试依赖；构建专属入口可能仍需独立编译 |
| 新增/修改并发 | `go test -race ./path/to/package/...` | 平台/架构/CGO 支持；通过仅说明覆盖到的执行没有报告 race |
| 输入边界与性能 | 既有 fuzz/benchmark/profile | 风险或性能目标需要时执行，不默认无限运行 |

## 验证场景

- error：超时、取消、缺失/损坏数据，`errors.Is/As` 可识别，typed nil 不误报成功。
- 并发：停止并等待、阻塞收发、重复关闭、共享状态一致性；测试本身不数据竞争，不用固定睡眠赌调度。
- 资源：打开失败与成功后的关闭、事务回滚和提交失败、HTTP 状态与 body 读取失败。
- 兼容：旧 JSON/Proto/配置、nil 与空集合、最低 Go 版本；跨 Module 改动分别验证。
- 持久化：唯一约束、重复请求、事务/查询实际语义用组件或集成测试；Mock 不证明真实数据库正确。

按改动选择必要测试，低风险机械修改不强制新增单测。已有 bug 可构造稳定失败条件时补针对性回归用例。

## 审查卡

重点核对 GO-TYPE 的复制与 nil、GO-ERR 的因果、GO-CONC 的退出与同步、GO-RES 的释放、GO-COMPAT 的模块与协议。报告证据和最小改法，不要求所有项目采用同一架构。

交付记录 Module、工具链、命令、tags、结果及环境限制；未跑 race 或集成测试应明确，不写成全部通过。
