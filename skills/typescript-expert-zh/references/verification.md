# TypeScript 验证与审查

## 选择实际入口

先读 `package.json`、锁文件、CI、`tsconfig` 及 formatter/linter 配置。沿用现有包管理器、workspace 过滤方式与脚本；不运行会临时下载新版本工具的命令，不擅自安装或升级依赖。

| 目标 | 优先检查 | 局限 |
|---|---|---|
| 类型与声明 | 仓库 typecheck/build 脚本；无封装时使用已安装的 `tsc --noEmit -p tsconfig.json` | 项目引用、声明产物与打包可能需独立构建；类型不能代替运行时校验 |
| 逻辑与排版 | 现有 ESLint 和 formatter 的检查模式 | 避免全仓自动修复造成无关差异 |
| 行为 | 现有测试框架的目标模块测试 | 用可观察结果断言，不照着实现做快照 |
| 发布接口 | 声明、导出、生成源和实际运行产物检查 | 只通过源码 typecheck 不代表消费者能导入 |

## 与风险匹配的验证

- 解析/类型守卫：合法值、缺失、`null`、错误类型、额外字段策略、长度及数值上下界。
- 异步变更：拒绝、取消、超时、重复提交、乱序响应、部分成功与清理；避免依赖真实睡眠验证先后顺序。
- 对外契约：旧调用方、新旧字段组合、JSON/日期/金额表示、ESM/CJS 入口及目标运行时。
- 安全边界：授权失败、HTML/消息来源、路径或 URL 绕过；测试使用隔离样本，不访问生产资源。

仅文案或机械格式修改通常只需相关格式/构建检查；行为修改按风险补充测试，不机械新增全部场景。性能改动才要求相应 profile/benchmark。

## 审查卡

确认 TS-TYPE 的断言与空值证据、TS-ASYNC 的等待/取消归属、TS-SEC 的可信边界，以及 TS-COMPAT 的运行时和消费者兼容。只有能说明触发条件与实际影响的条目才报告为缺陷。

完成后记录实际命令、范围、结果及未执行原因；不要把工具缺失写成检查通过。
